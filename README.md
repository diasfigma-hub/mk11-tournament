# MK11 Arena

Турнирная платформа для соревнований по **Mortal Kombat 11**: регистрация бойцов в общее
лобби, турниры с расписанием и лимитом, жеребьёвка, сетка single elimination, ввод
результатов, матч за 3-е место и таблица мест.

Проект вырос из заброшенного шаблона спортивной регистрации (Vue 3 + Vite + mokky.dev):
спортивные поля и страницы убраны, добавлены данные и логика турниров по MK11.

**Текущий стек:** Vue 3 + Vite 8 + vue-router 5, Supabase (Postgres, Auth, Realtime),
размещение — Vercel (статика + SPA-rewrites). Своего Node-сервера нет.

## Что уже есть

**Публичная часть**

- главная страница с живой статистикой и ближайшими турнирами;
- регистрация бойца: игровой ник, ФИО, основной персонаж и необязательный контакт;
  проверка допустимого персонажа и защита от повторного ника на уровне базы;
- список турниров с фильтром по статусу;
- страница турнира: участники, статус и срок регистрации, лимит игроков,
  сетка, статусы матчей, результаты и таблица мест.

**Панель организатора** (`/admin/login`)

- вход через Supabase Auth по email и паролю;
- лобби бойцов: поиск, показ старых записей, сортировка, редактирование данных,
  статусы «допущен/снят», удаление;
- автоматическое обновление списка участников через Supabase Realtime;
- общий переключатель «Закрыть/Открыть регистрацию» для всего лобби;
- создание турнира: название, описание и правила, дата старта, срок регистрации,
  лимит игроков, платформа, Bo матчей и гранд-финала;
- жеребьёвка: выбор состава из лобби с учётом лимита, случайное распределение пар,
  автоматические баи при неполной сетке;
- сетка на 2–32 участника: счёт вносится кнопками (`2:0`, `3:2`, …), победитель
  автоматически проходит дальше, изменение результата отменяет следующие раунды;
- отдельный матч за 3-е место при 4 и более участниках;
- ник и ФИО показываются в сетке, составе и таблице мест;
- автоопределение чемпиона и таблицы мест (`1`, `2`, `3`, `4`, `5–8`, …).

## Запуск

```bash

npm run dev      # http://localhost:5173
npm run build
npm run preview
```

Для работы нужны переменные окружения Supabase (см. ниже). Без них приложение

## Настройка Supabase

### 1. Создайте проект

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте новый проект.
2. Запишите **Project URL** и **anon public key**: Project Settings → API.
3. `service_role` key в приложение не добавляйте: он обходит RLS и не должен
   попадать в браузер, репозиторий или переменные с префиксом `VITE_`.

### 2. Выполните схему

Откройте **SQL Editor** и целиком выполните файл [`supabase/schema.sql`](supabase/schema.sql).
Он создаёт:

- `participants` — участники, уникальный ник без учёта регистра, проверка 24 персонажей,
  ограничения длины, дата регистрации;
- `tournaments` — турниры, составы, сетки, матч за 3-е место, чемпион;
- `settings` — одна строка с общим флагом закрытия регистрации;
- `admin_users` — список пользователей Supabase Auth с правами организатора;
- RLS-политики, публичный счётчик `participant_count()` и публикацию Realtime.

Скрипт можно запускать повторно: таблицы и индексы создаются с `IF NOT EXISTS`,
политики пересоздаются.

### 3. Настройте Auth

1. Authentication → Sign In / Providers → Email: включите Email-провайдер.
2. Authentication → Settings: **отключите** «Allow new users to sign up».
3. Authentication → Users → **Add user**: создайте администратора с нужным email
   и паролем. Включите «Auto Confirm User», чтобы не зависеть от письма.
4. Выдайте ему права организатора — выполните в SQL Editor, подставив свой email:

```sql
insert into public.admin_users (user_id)
select id from auth.users where email = 'you@example.com'
on conflict (user_id) do nothing;
```

Без записи в `admin_users` вход отклоняется: приложение после Supabase Auth
вызывает `is_admin()`, разлогинивает такой аккаунт и показывает сообщение об
отсутствии прав. Это сделано намеренно: даже при случайно включённой регистрации
новый пользователь не станет администратором.

### 4. Пропишите переменные локально

Скопируйте `.env.example` в `.env` и заполните:

```bash
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
```

`anon` key публичный по назначению: доступ ограничивают RLS-политики. `.env`
уже в `.gitignore`.

## Модель безопасности

- **Посетитель (аноним или вошедший пользователь)** может только добавить
  участника. Ему разрешены колонки `nickname`, `full_name`, `main_character`,
  `contact`; `status` и `created_at` заполняются значениями по умолчанию.
- **Читать участников без прав администратора нельзя**: контакты не попадают
  в публичные ответы. Главная и форма регистрации получают только число через
  `participant_count()`.
- **Изменять и удалять** участников, турниры и настройки может только пользователь
  из `admin_users`; проверка идёт через `is_admin()` в RLS.
- **Повторный ник** блокируется уникальным индексом `lower(btrim(nickname))`,
  а не только проверкой в браузере.
- **Персонажи** ограничены CHECK-констрейнтом 24 базовыми бойцами; DLC вставить нельзя.
- **Закрытие регистрации** проверяется в RLS-политике `INSERT`: при закрытом лобби
  заявка отклоняется даже при ручном запросе к API.
- **Публичный API турниров** читает представление `public_tournaments`: только ник, персонаж, сетка и результаты. ФИО и контакты в него не попадают. Базовая таблица `tournaments` доступна только администратору.
- Пароль администратора хранится в Supabase Auth, в клиентском коде его нет.

## Миграция безопасности для существующей базы

Если база Supabase уже создана, выполните в SQL Editor файл
[`supabase/security_hardening.sql`](supabase/security_hardening.sql) от имени
владельца таблиц (роль `postgres`). Скрипт не удаляет таблицы и строки, не
меняет существующие JSON-снимки и ID, не трогает дизайн сайта. Повторный запуск
безопасен.

### Что меняется

- Публичные страницы читают представления `public_tournaments` и
  `public_settings`. Базовая таблица `tournaments` и `settings` доступна только
  администратору; `anon` не может их читать, менять или удалять.
- Перед публикацией JSON очищается рекурсивно: удаляются `fullName`, `contact`,
  `email`, `phone`, мессенджеры и даты рождения на любой глубине.
- Внутренние числовые ID (`id`, `winnerId`, `p1`/`p2`) заменяются на стабильные
  псевдонимы — усечённый HMAC-SHA256 с секретным ключом. Обычный `md5` с
  постоянным префиксом не годится: последовательные ID перебираются мгновенно.
  Ключ хранится в закрытой таблице `app_secrets`, поэтому псевдонимы стабильны
  между запусками и одинаковы во всех полях сетки.
- Очищенные копии JSON (`public_players`, `public_rounds`, `public_third_place`,
  `public_champion`) пересчитываются триггером при каждой записи турнира.
  Представление не вызывает функций, поэтому `anon` не получает `EXECUTE` на
  очистку и не может использовать её как оракул «ID → псевдоним».
- Проверка «регистрация открыта» вынесена в `registration_open()`:
  RLS-политика `INSERT` больше не читает `settings` от имени анонима, иначе
  регистрация падала бы после отзыва `SELECT`.
- Публичный `SELECT` на `participants` по-прежнему закрыт, `RETURNING` для
  анонима недоступен. `supabase-js` без `.select()` его не запрашивает.
- Турниры и `settings` исключаются из публикации Realtime: она отдаёт строку
  целиком, обходя колонки представления.
- `is_published` (по умолчанию `true`) позволяет скрыть турнир из публичного API,
  не удаляя его: `update public.tournaments set is_published = false where id = …`.
  Статус `draft` намеренно остаётся публичным: в этом проекте это «Набор
  участников» с открытой регистрацией, он есть в фильтре `/tournaments` и в
  блоке «Ближайшие турниры» на главной.

### Проверка после применения

```sql
select has_table_privilege('anon', 'public.tournaments', 'SELECT');        -- false
select has_table_privilege('anon', 'public.settings', 'SELECT');           -- false
select has_table_privilege('anon', 'public.public_tournaments', 'SELECT'); -- true
select has_table_privilege('anon', 'public.tournaments', 'UPDATE');        -- false
select has_function_privilege('anon', 'public.public_tournament_json(jsonb)', 'EXECUTE'); -- false
select * from public.public_tournaments;  -- JSON без ФИО и контактов
```

Полный чек-лист (политики, доступные `anon` функции, публикация Realtime)
приведён в конце `supabase/security_hardening.sql`.

### Откат

[`supabase/security_hardening_rollback.sql`](supabase/security_hardening_rollback.sql)
возвращает прежние `GRANT` и RLS-политики, удаляет представления, функции,
триггер и служебные колонки. Таблицы, строки, ID и исходные JSON не трогаются.
Учтите: после отката ФИО снова станут публичными, а фронтенд нужно вернуть на
прямое чтение таблиц.

### Совместимость

Скрипт рассчитан на PostgreSQL 12+ (Supabase использует 15/17) и не применяет
синтаксис новее 12-й версии. Нужен `pgcrypto` в схеме `extensions` — в Supabase
он установлен по умолчанию; при отсутствии скрипт остановится с понятной
ошибкой до внесения изменений.

### Порядок применения

1. Сделайте резервную копию: Supabase → Database → Backups (или `pg_dump` по
   строке подключения). Миграция данные не меняет, но копия обязательна.
2. Откройте SQL Editor и выполните [`supabase/migration_checks.sql`](supabase/migration_checks.sql),
   часть A. Ожидается: роль `postgres`, PostgreSQL 12+, `pgcrypto` в схеме
   `extensions`, владелец всех таблиц — `postgres`, представлений ещё нет.
   Скрипт только читает каталог.
3. Выполните целиком [`supabase/security_hardening.sql`](supabase/security_hardening.sql)
   в том же SQL Editor. Скрипт идёт одной транзакцией: при любой ошибке не
   применяется ничего. На существующей базе это секунды.
4. Выполните часть B файла `migration_checks.sql`: базовые таблицы закрыты,
   представления читаются, `public_*` без ФИО, `anon` не вызывает служебные
   функции, турниров и `settings` нет в публикации Realtime.
5. Проверьте REST (подставьте свой URL и anon-ключ):

   ```bash
   curl -i "$VITE_SUPABASE_URL/rest/v1/tournaments?select=*" \
     -H "apikey: $VITE_SUPABASE_ANON_KEY"      # 401 permission denied
   curl -i "$VITE_SUPABASE_URL/rest/v1/participants?select=*" \
     -H "apikey: $VITE_SUPABASE_ANON_KEY"      # 401 permission denied
   curl -i "$VITE_SUPABASE_URL/rest/v1/public_tournaments?select=*" \
     -H "apikey: $VITE_SUPABASE_ANON_KEY"      # 200, в JSON нет fullName
   curl -i "$VITE_SUPABASE_URL/rest/v1/public_settings?select=*" \
     -H "apikey: $VITE_SUPABASE_ANON_KEY"      # 200
   ```

6. Проверьте интерфейс: главная, `/tournaments`, страница турнира, отправка
   заявки, затем вход в `/admin`, создание турнира, жеребьёвка, ввод счёта,
   список участников и переключатель регистрации.
7. Только после этого коммитьте, пушьте и деплойте фронтенд: новый код читает
   `public_tournaments`/`public_settings`, которых до миграции не существует.

> **Важно про порядок.** Публичные страницы в текущем коде уже обращаются к
> представлениям. Если задеплоить фронтенд раньше миграции, `/tournaments`
> покажет ошибку, а страница турнира — «Турнир не найден». Сначала SQL, потом деплой.
>
> Если после миграции REST всё ещё отдаёт 404 на `public_tournaments`, обновите
> кэш схемы: SQL уже шлёт `notify pgrst, 'reload schema'`; повторно —
> Settings → API → Reload schema или `NOTIFY pgrst, 'reload schema';`.

## Публикация на Vercel

### Вариант A — через GitHub

1. Создайте репозиторий на GitHub и загрузите проект:
   ```bash
   git init
   git add .
   git commit -m "MK11 Arena: Supabase + Vercel"
   git branch -M main
   git remote add origin https://github.com/<user>/<repo>.git
   git push -u origin main
   ```
   `.env` в репозиторий не попадёт.
2. В Vercel: **Add New → Project → Import Git Repository**.
3. Framework Preset: **Vite**. Build Command: `npm run build`. Output Directory: `dist`.
4. В **Environment Variables** добавьте для Production и Preview:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
5. Нажмите **Deploy**. После сборки Vercel выдаст HTTPS-ссылку вида
   `https://<project>.vercel.app`.

### Вариант B — через CLI

```bash
npm i -g vercel
vercel login
vercel link
vercel env add VITE_SUPABASE_URL production
vercel env add VITE_SUPABASE_ANON_KEY production
vercel --prod
```

Переменные можно добавить и в панели Vercel → Project Settings → Environment Variables.
После изменения переменных нужен **новый деплой**: Vite встраивает их на этапе сборки.

### Маршруты и SPA

`vercel.json` перенаправляет все пути на `index.html`, поэтому прямые ссылки
`/register`, `/tournaments/1`, `/admin/login` работают и после обновления страницы.

### Проверка после деплоя

- открыть главную и `/register` — статистика и форма загружаются;
- зарегистрировать бойца с компьютера и с телефона;
- в админке `/admin/login` войти под созданным администратором и увидеть новую заявку
  без ручного обновления (Realtime);
- открыть `/tournaments/1` напрямую и обновить страницу — 404 быть не должно;
- проверить, что в исходниках страницы и в репозитории нет `service_role` key
  и пароля администратора.

- Без GitHub: `vercel --prod` из папки проекта.

## Закрытие регистрации

Админка → **Бойцы** → кнопка **«Закрыть регистрацию»**. Флаг общий для всего лобби:
форма регистрации показывает «Регистрация закрыта», а вставка новых участников
отклоняется политикой RLS. Кнопка **«Открыть регистрацию»** возвращает приём заявок.

## Realtime

Админ-страница «Бойцы» подписывается на изменения `public.participants` и обновляет
список при новых заявках. Публикация таблицы включается в `schema.sql`. Если Realtime
не работает, проверьте в SQL Editor:

```sql
select * from pg_publication_tables where pubname = 'supabase_realtime';
```

Если таблицы нет:

```sql
alter publication supabase_realtime add table public.participants;
```

Realtime соблюдает RLS, поэтому данные получает только вошедший администратор.

## Проверка безопасности вручную

Выполните в SQL Editor (подставьте ник существующего бойца):

```sql
-- Аноним не должен прочитать участников и контакты
set role anon;
select * from public.participants; -- ERROR: permission denied
delete from public.participants where true; -- ERROR: permission denied
reset role;

-- Аноним может вставить только разрешённого персонажа и корректные поля
set role anon;
insert into public.participants (nickname, full_name, main_character)
values ('qa_test', 'Тестов Тест', 'Spawn'); -- ERROR: check constraint
reset role;
```

Проверка закрытия регистрации: закройте её в админке и попробуйте отправить форму —
должно появиться сообщение об ошибке, а запись не создастся.

## Ограничения

- Самостоятельной заявки на конкретный турнир нет: игрок регистрируется в общее
  лобби, состав турнира собирает организатор.
- Закрытие регистрации общее для лобби, а не отдельное для каждого турнира.
- Только один формат сетки — single elimination; данные турнира содержат поле
  `format`, построение вынесено в `src/lib/bracket.js`.
- Результаты матчей вносит только организатор: подтверждения от игроков нет.
- Supabase Auth отвечает за вход, но роль администратора определяется записью
  в `admin_users`. Удаление пользователя из Auth удаляет и его доступ.

## Данные MK11

Ростер персонажей вынесен в `src/lib/constants.js` и ограничен базовой версией
Mortal Kombat 11 — 24 бойца, включая Фрост. Платные DLC (Kombat Pack 1, Aftermath,
Kombat Pack 2) в форме регистрации и новых составах недоступны; устаревшее значение
DLC из старой записи сохраняется, но не попадает в новые турнирные составы;
в админ-лобби такого бойца можно перевести на разрешённого персонажа.

Формат матчей (Bo3/Bo5) и гранд-финала задаётся при создании турнира; способ
жеребьёвки — случайный выбор пар, это явно указано в интерфейсе.

Проект не использует официальные логотипы, арты или портреты персонажей; оформление
оригинальное, на основе прежней тёмно-золотой палитры.
